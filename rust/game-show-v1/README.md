# game-show-v1 — `wheel_stage` in Rust and three-d

A Rust application that renders the Blender scene `wheel_stage.blend` with the
[`three-d`](https://crates.io/crates/three-d) crate. The target look is `docs/wheel_stage.png`,
an illustration of the same set.

Geometry, materials, the camera and the lights all come out of Blender. Nothing in `src/` is
hand-modelled. The Blender file is exported to `assets/wheel_stage.glb` and to a manifest
`assets/scene.json`, and the Rust app reads only those two files at runtime. The app is offline:
it downloads nothing and reaches no network.

The binary has two modes. Without arguments it opens an interactive viewer with the wheel
spinning. With `--shot` it renders one deterministic frame offscreen at 1672x941 and exits.

## Requirements

- macOS with a GPU that gives OpenGL 3.3. Both modes need a GL context, so `--shot` opens a
  hidden 32x32 window (`src/shot.rs` explains why: `three-d` 0.19 dropped `HeadlessContext`).
- Rust 1.97.1 or newer, through `rustup`. If `which cargo` fails, run
  `export PATH="$HOME/.cargo/bin:$PATH"` first. Homebrew's `rustup` formula does not always
  create the shims.
- Blender 5.1 at `/Applications/Blender.app/Contents/MacOS/Blender`, for the export only. The
  app itself never calls Blender.
- Python 3 for `tools/validate_export.py`. It uses the standard library alone.

Run every command below from the crate root. Every asset and output path in this crate is
relative to it.

## Re-export from Blender

The export is only needed after the .blend changes. `assets/wheel_stage.glb` is committed.

```sh
/Applications/Blender.app/Contents/MacOS/Blender --background \
  ../../unity/blender-assets/wheel_stage.blend \
  --python tools/export_gltf.py
```

That writes `assets/wheel_stage.glb`. An output path may follow `--`:

```sh
/Applications/Blender.app/Contents/MacOS/Blender --background \
  ../../unity/blender-assets/wheel_stage.blend \
  --python tools/export_gltf.py -- renders/probe.glb
```

Then validate the result:

```sh
python3 tools/validate_export.py
```

The validator runs 33 checks over the GLB and prints `VALIDATION PASSED` on success. It takes
an optional path argument and otherwise checks `assets/wheel_stage.glb`.

**The .blend is never saved.** The Unity project shares that file and the author works in it.
`tools/export_gltf.py` runs under `--background`, which gets its own copy of the process state,
and it calls neither `save_mainfile` nor `save_as_mainfile`. Confirm the invariant after any
export:

```sh
stat -f '%Sm' -t '%Y-%m-%dT%H:%M:%S' ../../unity/blender-assets/wheel_stage.blend
```

Two more things to know about the export:

- **The manifest is not regenerated by that script.** `assets/scene.json` holds what a GLB
  cannot carry: the camera, all six lights, the material table, the spin pivot and the flapper
  geometry. It was measured from the .blend by hand, and its material entries were then tuned
  during look-dev, so re-exporting the GLB does not overwrite it. Re-measure it by hand if the
  .blend's lights, camera or materials change.
- **The export is not byte-reproducible, and that is harmless.** Two consecutive runs of the
  same script on the same .blend give a GLB with an identical JSON chunk and 38 differing bytes
  in the binary chunk. All 38 sit in the `TEXCOORD_0` floats of three primitives —
  `Wheel_Legs` slots 0 and 1, and `Podium_Trim` slot 1. Positions, normals and indices are
  identical. Those three primitives use untextured materials, so the UVs are never read and the
  rendered PNG comes out byte-identical either way.

## Run the viewer

```sh
cargo run --release
```

### Controls

| Input | Effect |
| --- | --- |
| drag | orbit the camera around the wheel |
| scroll or pinch | zoom, between 1 m and 60 m from the target |
| space | kick the wheel: it spins up, then coasts down under friction |
| `R` or `Home` | back to the hero view, `Cam_Hero` from the manifest |
| `Esc` | quit |

The same list is printed on start-up, because a window has nowhere to put it.

The wheel turns at a constant idle rate until the first kick. From then on it runs on the
free-running drive, which integrates a velocity and so is the only drive a kick survives.

## Take a shot

```sh
cargo run --release -- --shot renders/final.png
cargo run --release -- --shot renders/final.png --crops renders/crops_final
```

`--shot` renders one frame at 1672x941 from `Cam_Hero` with the wheel at rotation 0, writes the
PNG and exits. It reads no wall-clock value, so the same build always produces the same bytes.
`--crops <dir>` also writes the six comparison regions as `<dir>/<name>.png`.

| Crop | x | y | w | h | What it checks |
| --- | --- | --- | --- | --- | --- |
| `hub` | 700 | 300 | 300 | 300 | hub metal, spoke convergence, sector inner ends |
| `rim_top` | 620 | 110 | 460 | 210 | gold rim, bulb glow, crest crystal base |
| `floor` | 420 | 760 | 620 | 180 | floor gloss, reflection falloff, ring inlays |
| `screen_left` | 0 | 240 | 420 | 400 | LED wall colour and cloud shape |
| `truss` | 150 | 0 | 500 | 260 | truss silhouette, moving heads, beam cones |
| `podium` | 130 | 600 | 390 | 300 | podium trim, desk, its own reflection |

The reference crops for the same six rectangles are committed at
`renders/ref_crops/<name>.png`. Any other rectangle can be cut from either image with the
second binary:

```sh
cargo run --release --bin crop -- docs/wheel_stage.png renders/ref_crops/x.png 560 850 560 91
```

`x,y` is the top-left corner and y grows downward, matching the reference image's pixel
coordinates.

`renders/` and `target/` are both gitignored.

One diagnostic exists: `GS_LIGHT_AUDIT=1` makes `src/lighting.rs` print the rig it built, one
line per light, with the Blender type, the three-d type it became, the watts, the conversion
constant, the resulting intensity, and the position and direction actually used.

## Layout of `src/`

Each module has one owner. The owner's name is in the file's header comment, and the module map
in `docs/agent_plan.md` is the authority.

| File | What it does |
| --- | --- |
| `src/main.rs` | Window, event loop, argument parsing, and `World`, which owns everything drawn. The viewer and `--shot` drive the same `World`, so they cannot drift apart. |
| `src/manifest.rs` | Serde types for `assets/scene.json`. `three-d-asset` 0.10 reads neither cameras nor lights out of a glTF file, so the manifest is mandatory. |
| `src/scene.rs` | Loads the GLB, builds one part per named node, maps Blender materials onto `PhysicalMaterial`, applies the per-node look overrides, and derives the hero camera. |
| `src/lighting.rs` | The six Blender lights as three-d lights, watts converted per light, an ambient environment term built from the LED wall, and the shadow map on `Key_Wheel`. |
| `src/postfx.rs` | The whole frame chain: HDR target, bright pass, two blurs, bloom, floor reflection, lens flare, sparkles, vignette, tone map. Also the 38 additive beam cones. |
| `src/screen.rs` | The LED wall. Draws the author's exported `T_LEDWall_Sky` at emissive strength 1.5, with a procedural GLSL sky behind a constant as the fallback. |
| `src/spin.rs` | Wheel spin state and the flapper deflecting against the 48 pegs. Two drives: constant rate, and free-running with friction and detents. |
| `src/shot.rs` | The hidden-window GL context, the deterministic offscreen render, and the crop table. |
| `src/bin/crop.rs` | The standalone crop helper above. It is a second binary, which is why `Cargo.toml` sets `default-run`. |

`tools/export_gltf.py` and `tools/validate_export.py` are the Blender side. The exporter checks
every invariant the Rust side depends on and exits non-zero if one fails.

## Where the tunable look constants live

Every value that was tuned by eye is a named `pub const` at the top of its module, with a doc
comment saying what it does and which crop shows it. Nothing is a bare literal buried in a
shader string. The groups:

| Where | Constants |
| --- | --- |
| `src/lighting.rs` | `*_WATTS_TO_INTENSITY` per light, then `KEY_LOOK_GAIN`, `RIM_LOOK_GAIN`, `FILL_LOOK_GAIN`, the `BULB_RING_*` family, `AMBIENT_INTENSITY`, the `ENVIRONMENT_*` family, `SHADOW_MAP_SIZE`, `SHADOW_REFRESH_INTERVAL` |
| `src/postfx.rs` | `EXPOSURE`, `TONE_MAPPING`, the `BLOOM_*` family, the `VIGNETTE_*` family, the `BEAM_*` and `PAR_*` families, the `REFLECTION_*` family, the `FLARE_*` family, the `SPARKLE_*` family, `SHADOW_LIFT*` |
| `src/screen.rs` | `SCREEN_*` for the exported texture's grade, `FORCE_PROCEDURAL_SKY` to switch paths, then `SKY_*`, `CLOUD_*` and `STAR_*` for the procedural sky |
| `src/scene.rs` | `HUB_*` for the hub's anisotropic shader, `CRYSTAL_LOOK_EMISSION`, `GOLD_TRIM_LOOK_*`, `HUB_RING_NODE`, `HUB_RIVET_NODE`, and `NODE_LIFTS`, the table of per-node material overrides |
| `src/main.rs` | `SCREEN_DRAWN_BY_SCREEN_RS`, `ORBIT_DISTANCE` |
| `src/spin.rs` | `KICK_RATE`, `MAX_RATE`, `AIR_DRAG`, `BEARING_FRICTION`, `DETENT_STIFFNESS`, and the `TICK_*` and `RING_*` flapper constants |
| `assets/scene.json` | The material table itself. Some entries carry a look-dev override beside the measured Blender value, with a note saying why. |

The measured Blender values are the baseline in all cases. A look constant is always a
multiplier or an override on top of one, so the ground truth stays readable next to it.

## What does not match the reference, and why

Judged by eye on the six crop pairs plus extra rectangles, at 1x and at 2x. No histogram, mean
brightness or similarity score was used, and none should be: that approach degraded this scene
once already.

The frame reads as the right picture. Composition, camera, silhouette, sector fan, pillars,
podium, truss and LED cyclorama are all in the right place at the right scale, and they are in
the right place because they come from the GLB. What is left is value and chroma, in a few
places, plus a handful of things the reference simply does not share with the Blender file.

**Structural, and not worth chasing.** The reference is an illustration, not a render of this
.blend:

- Its wheel has about 24 wide sectors with jewelled studs. The Blender wheel has 48 thinner
  sectors and a 96-bulb ring. The sector count, the proportion of magenta to cream in the fan,
  and the wheel's scale and position all come from the GLB.
- Its truss is a deeper, denser rig with confetti in the air. Collection `60_Rig` holds one ring
  with an inner ring, twelve moving heads and six blinders. The silhouette reads correctly; the
  member count cannot.
- Its podium sits about 40 px higher in the frame, and the LED wall is one unbroken screen. The
  Blender wall is crossed by `Wall_Band_Mid`, `Wall_Band_Up` and `Wall_Fascia`, so three gold
  bands cut across the sky. Both are geometry.
- Its cyclorama is a painted sunset with big coral cumulus. The wall in the render shows
  `T_LEDWall_Sky`, the author's own 4096x1024 texture out of the .blend, which is a smoother
  violet-and-cobalt sky with thin cloud. The art differs at source.

**Look, still open.** These are real gaps and they were the last look-dev round's asks:

1. **The strip under the wheel is dead.** At 560,850 the render gives a flat dark plum slab over
   a dull mauve band. The reference gives a bright gold-and-magenta glossy floor with vertical
   light streaks. `Wheel_BasePlate` carries `MAT_Dark_Trim` and renders as one flat value, so the
   floor reflection has nothing bright to mirror there. This is the largest remaining gap and it
   sits in the lower centre of the frame.
2. **The right-hand wall has no cloud structure.** The right side of the cyclorama is a flat
   electric cobalt with small pale stratus. The reference has big cyan-white and pink lobes over
   cobalt. The left side is closer but still short of the reference's value range: it has the
   magenta and the lilac, not the coral and the peach.
3. **Lifted golds read closer to khaki than to gold.** The wall bands, the podium desk band, the
   podium ribs and the floor ring inlays are each a broad flat band. The reference draws every
   one as a thin saturated gold line with a hard dark groove beside it. The per-node emissive
   lift has no gradient across a band's width.
4. **The crest is soft.** It is a lavender mushroom with an even glow. The reference is a
   faceted magenta crystal with hard bevels and a thin white spike.
5. **The rim's band stack is thin.** The render draws one gold hoop about 25 px deep. The
   reference stacks groove, gold, dark line, gold and chrome over about 45 px. The pegs also
   want one small hard specular each and currently have none.
6. **The hub bezel keeps a visible ring of dark rivets.** The reference bezel is an unbroken
   violet-chrome ring. The hub dome itself was fixed in the last round and now reads as a
   violet-silver disc with about ten broad wedges, which is right.

The look-dev record is in `docs/lookdev_log.md`. It has one section per round: what the frame
looked like, crop by crop, what the previous round fixed, what did not land, and what the next
round asked for. Five rounds ran and the last one did not converge, so the list above is where it
stopped rather than a set of unknowns.
