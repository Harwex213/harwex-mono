1. The Problem

We need a dev environment to preview and iterate on UI kit components in isolation. Storybook is the obvious choice, but it is heavy: large node_modules footprint, slow cold starts, complex configuration, and its own build pipeline.

Our stack: React 19 + TypeScript 5.9 + Vite 7 + CSS Modules. We want something that works with this stack with minimal friction.

Requirements: see components rendered with variants/states, hot reload on changes, minimal dependencies, no complex build setup.

2. Lightweight Dedicated Tools

Ladle Promising but risky

Ladle — a Vite-native, React-only Storybook alternative. ~2.9k stars. Uses the same .stories.tsx format (CSF 3.0 compatible). Zero-config.

AspectDetail
Install weight~20x smaller page weight than Storybook. Build output ~2-4 MB vs Storybook's ~7-16 MB
Setupnpm i @ladle/react + write .stories.tsx files. Zero-config.
React 19Supported since v5.0.0
Vite 7Broken — HMR fails due to Rolldown changes ("Missing field moduleType"). Open issue, unresolved. Must pin Vite 6 for Ladle.
HMRFull Vite HMR. ~1.2s cold start for 50 stories
MaintenanceSingle maintainer. Last release Nov 2024. Activity slowing.

Verdict: Best lightweight tool in concept, but Vite 7 incompatibility and slowing maintenance make it risky for our stack.

React Cosmos Solid alternative

React Cosmos — component sandbox using "fixtures" instead of "stories." 8.6k stars. Established since 2014.

AspectDetail
Install weightMinimal. ESM-only. Lighter than Storybook, slightly heavier than Ladle
Setupnpm i react-cosmos react-cosmos-plugin-vite + cosmos.config.json + .fixture.tsx files
React 19Supported since v7.0.0
Vite 7Untested — latest release v7.2.0 (March 2025). Needs testing.
HMRFull Vite HMR via plugin
MaintenanceActively maintained through early 2025. Consistent releases.

Verdict: More mature and better maintained than Ladle. Worth testing with Vite 7.

Eliminated Options

  • Histoire — Vue/Svelte only. No React support.
  • React Styleguidist — Webpack-only (no Vite). Effectively dead.
  • StoryLite — Experimental, unmaintained. Too risky.
  • vite-plugin-react-pages — Archived Dec 2025. Dead.

3. DIY Vite Showcase Page Recommended

Create a dedicated page within your existing Vite app that renders all components with their variants. Zero new dependencies. Guaranteed Vite 7 + React 19 compatibility.

Pattern A: Separate Vite entry point CHOSEN

A standalone HTML entry that Vite serves alongside your main app.

// File structure
src/
  showcase/
    index.html            // separate HTML entry
    main.tsx              // React root
    ShowcaseApp.tsx        // sidebar nav + component display
    entries/
      ButtonShowcase.tsx
      ModalShowcase.tsx
      ...

// vite.config.ts — add showcase as a second entry
export default defineConfig({
  build: {
    rollupOptions: {
      input: {
        main: 'index.html',
        showcase: 'src/showcase/index.html',
      },
    },
  },
});

Pro: Fully isolated from your game UI. Own HTML, own React root.
Con: Slightly more setup (second entry point in Vite config).

Pattern B: Dev-only route

Add a route that only exists in development mode.

// Conditionally render showcase in dev
if (import.meta.env.DEV) {
  // render <ShowcaseApp /> when URL has ?showcase param
}

Pro: Simplest setup — no config changes.
Con: Shares the app's React root; may interfere with MapEngine initialization.

Pattern C: Auto-discovery with import.meta.glob

Vite's glob import automatically discovers all showcase files. No manual registration needed.

// ShowcaseApp.tsx
const modules = import.meta.glob(
  '../ui/**/*.showcase.tsx',
  { eager: true }
);

// Each module exports: { name: string, render: () => ReactNode }
const entries = Object.values(modules).map(
  (m) => (m as any).default
);

// src/ui/button/Button.showcase.tsx
export default {
  name: 'Button',
  render: () => (
    <div>
      <h3>Default</h3>
      <Button>Click me</Button>

      <h3>Disabled</h3>
      <Button disabled>Disabled</Button>

      <h3>Variants</h3>
      <Button variant="primary">Primary</Button>
      <Button variant="ghost">Ghost</Button>
    </div>
  ),
};

Pro: Add a .showcase.tsx next to any component and it appears automatically.
Con: You build the shell UI yourself (sidebar, layout — ~50-100 lines).

What the showcase shell looks like (~60 lines)

// ShowcaseApp.tsx — the entire shell
import { useState } from 'react';

type TShowcaseEntry = {
  name: string;
  render: () => React.ReactNode;
};

const modules = import.meta.glob(
  '../ui/**/*.showcase.tsx',
  { eager: true }
);

const entries: TShowcaseEntry[] = Object.values(modules)
  .map((m) => (m as any).default)
  .filter(Boolean);

export function ShowcaseApp() {
  const [selected, setSelected] = useState(entries[0]?.name);
  const active = entries.find((e) => e.name === selected);

  return (
    <div style={{ display: 'flex', height: '100dvh' }}>
      <nav style={{ width: 220, borderRight: '1px solid #30363d',
                     padding: '1rem', overflowY: 'auto' }}>
        <h2 style={{ color: '#58a6ff', fontSize: '1rem' }}>UI Kit</h2>
        {entries.map((e) => (
          <button
            key={e.name}
            onClick={() => setSelected(e.name)}
            style={{
              display: 'block', width: '100%',
              textAlign: 'left',
              padding: '6px 8px', margin: '2px 0',
              background: selected === e.name
                ? '#1c2129' : 'transparent',
              color: '#e6edf3', border: 'none',
              borderRadius: 4, cursor: 'pointer',
            }}
          >
            {e.name}
          </button>
        ))}
      </nav>
      <main style={{ flex: 1, padding: '2rem',
                      overflowY: 'auto' }}>
        {active ? active.render() : 'Select a component'}
      </main>
    </div>
  );
}

That's the entire showcase infrastructure. ~60 lines. Full Vite HMR. Zero dependencies.

4. Doc-Based Approaches Overkill

Tools like Docusaurus and Astro + Starlight can render live React components in MDX. However:

  • Docusaurus: ~150+ MB node_modules, uses Webpack internally (not Vite), separate build pipeline
  • Astro: its own framework, had Vite 7 compatibility issues, separate build

These are documentation site generators, not component dev environments. Eliminated for our use case.

6. Decision: DIY Vite Showcase — Pattern A (Separate Entry Point)

DECIDED We will implement Pattern A: a separate Vite entry point with auto-discovery (Pattern C) for component registration.

Why DIY over third-party tools:

  • Zero dependency risk — no third-party tool to break with Vite 7. Ladle is already broken; Cosmos is untested.
  • Zero learning curve — it's just React + CSS Modules, the same as our components.
  • Zero build complexity — same Vite process, same HMR, same everything.

Why Pattern A over B and C:

  • Full isolation — separate HTML entry + React root, no interference with MapEngine initialization.
  • Clean separation — showcase has its own index.html, own styles, own mount point. The game app doesn't know it exists.
  • Combined with Pattern C's auto-discovery — import.meta.glob('**/*.showcase.tsx') inside the separate entry, so adding components is still zero-config.

Implementation plan:

  1. Create src/showcase/index.html — standalone HTML entry
  2. Create src/showcase/main.tsx — React root for showcase
  3. Create src/showcase/ShowcaseApp.tsx — sidebar nav + component display shell, using import.meta.glob for auto-discovery
  4. Update vite.config.ts — add showcase as second input entry
  5. Add "showcase" npm script
  6. For each UI component, co-locate a ComponentName.showcase.tsx that renders all variants

When to reconsider: If we grow beyond ~20 components and need prop controls, viewport toggling, or visual regression testing — then evaluate React Cosmos or Storybook 10.
