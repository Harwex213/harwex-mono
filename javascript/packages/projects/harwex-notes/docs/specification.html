Harwex Notes Specification

A local single-page app over one folder on disk. A file tree on the left, a tab bar and one viewer on the right. Drawings, Markdown and plain text are edited in place and saved without a command; HTML is rendered and never edited.

This document defines behaviour, not implementation. Every rule carries an identifier and can be walked through in the running app and marked pass or fail. It says nothing about frameworks, transports or file layout.

01 Purpose

One folder on the user's machine holds notes in four forms: Excalidraw drawings, Markdown documents, plain text files and HTML pages. Today each form needs a different program. This app opens all four in one place, in a browser, against the folder as it sits on disk.

The folder is the model. There is no database, no account and no copy of the content anywhere else. What the app shows is what the disk holds, and an edit in the app is an edit to the file.

02 Vocabulary

TermMeaning
VaultThe one folder the app opens. Everything the app can read or write lives inside it.
EntryA file or a folder inside the vault.
Supported fileA file the app can open, decided by its extension. See VAULT-2.
ViewerThe surface that shows one open file. Four exist: drawing, Markdown, text, HTML.
TabOne open file in the tab bar. At most five exist at once.
DocumentThe content of one open file as the app holds it, together with its save state.
Unsaved changesA document differs from the file on disk because the user edited it and the save has not landed yet.
ConflictA document has unsaved changes and the file on disk changed since the app read it.
FilterA term in the search field. While the field holds a term the tree shows matching entries only.
MatchAn entry whose name contains the term, or an openable file whose content contains it.

Two columns. The left column holds a search field over the file tree of the whole vault. The right column is a tab bar over one viewer, and the viewer fills the rest of the height. The divider between the columns is draggable. Nothing else is on the screen: no menu bar, no sidebar, no second route.

04 APP — Application shell

IDRule
APP-1The app runs at a fixed address on the local machine. That address is the whole app: one screen, one URL. Nothing in the app navigates the browser away from it.
APP-2The app opens exactly one vault. Changing the vault requires restarting the app.
APP-4Opening the same address in a second browser tab is allowed. Each tab is a full, independent client. The files on disk are the only state the two share, and two clients editing one file resolve the collision under the CONF rules.
APP-5While any document has unsaved changes, a save is in progress, or a conflict is unresolved, the browser asks the user to confirm leaving the page. The wording of that prompt belongs to the browser and the app cannot change it.
APP-6APP-5 cannot stop a forced close. When the page is closing anyway, the app makes one last attempt to write every pending save. This document does not claim that attempt always succeeds.
APP-7The app needs no login and no network beyond the user's own machine.
On APP-5. A browser will not let a page block its own closing. The strongest available behaviour is the browser's own confirmation prompt, and a user who confirms it closes the page. The spec states this plainly so that no reviewer expects a hard block.

05 VAULT — The vault and its files

IDRule
VAULT-1Every file and every folder in the vault appears in the tree. Nothing is hidden because of its type.
VAULT-2Six extensions are supported, matched without regard to case: .excalidraw, .md, .markdown, .txt, .html, .htm.
VAULT-3Every other file is shown, marked visibly as not openable, and cannot be opened.
VAULT-4A file larger than 8 MB is refused when the user tries to open it. The refusal names the size limit and no tab opens.
VAULT-5A supported file whose content is not readable text is refused the same way. The refusal states that the file is not text.
VAULT-6A vault too large to list is refused at startup, with a message naming the reason. The app never shows part of a vault as though it were the whole vault.
VAULT-7The app reads and writes only inside the vault. An entry that points outside the vault is listed but never followed, and the app never opens or writes the target.
VAULT-8Folders that hold generated content — dependency folders, build output, version-control internals — are not listed. This keeps a vault that also happens to be a project directory usable.

06 TREE — File tree

IDRule
TREE-1The tree shows the whole vault: every folder and every file, nested as they are on disk.
TREE-2A single click selects a row. Selection opens nothing and expands nothing.
TREE-3A double click on a supported file opens it. A double click on a folder expands it, or collapses it when it is already expanded.
TREE-4Collapsing a folder also collapses every expanded folder inside it. Expanding that folder again shows its children collapsed.
TREE-5The tree is usable from the keyboard. Up and Down move through the visible rows. Right expands a folder. Left collapses a folder, or moves to the parent when the row is already collapsed. Enter opens a file or toggles a folder. F2 starts a rename. Delete starts a deletion. The whole panel is a single tab stop.
TREE-6Inside a folder, folders come first, then files. Both are sorted by name without regard to case.
TREE-7The width of the tree panel is adjustable by dragging the divider.
TREE-8A change to the vault made outside the app does not disturb the selected row or the set of expanded folders. See SYNC-2.
TREE-9Each row shows the entry name and a marker for its kind. Folders show whether they are expanded.

07 SRCH — Search

IDRule
SRCH-1A search field sits above the tree, in the same panel. The app has no other search surface.
SRCH-2The tree itself shows the results. While the field holds a term, only matching entries are listed, each under the real folders that hold it, and those folders are expanded so the path to every match is visible.
SRCH-3Clearing the field restores the tree as it was before the search, including which folders the user had expanded and which row was selected.
SRCH-4Every entry matches on its name, folders included.
SRCH-5Content is searched in the openable text kinds: Markdown, plain text and HTML.
SRCH-6Inside a drawing, only the text the user typed into the drawing is searched. The data that describes the shapes is never searched, because it would match on identifiers and colours that the user cannot see.
SRCH-7A file that cannot be opened — an unsupported extension, too large, not text — matches on its name alone.
SRCH-8Search covers exactly what the tree shows. The folders excluded by VAULT-8 are not searched, and nothing outside the vault is searched.
SRCH-9Matching ignores case and treats the term as plain text. There are no patterns, no wildcards and no options to configure.
SRCH-10A term of one character filters on names only. From two characters onward content is searched as well.
SRCH-11Results follow the field as the user types. No key needs to be pressed to run the search.
SRCH-12A file with unsaved changes is searched as the user has it, not as the disk holds it.
SRCH-13A row that matched on content shows how many times the term occurs in that file.
SRCH-14Opening a result follows the TAB rules. A Markdown or text file scrolls its first match into view. A drawing or an HTML file opens normally, without jumping to a match.
SRCH-15A filter stays live. A file created outside the app that matches appears in the results; a file edited so that it no longer matches leaves them; a deleted file disappears.
SRCH-16While a search over a large vault is still running the panel says so, and results appear as they are found. The panel never looks empty while it is still working.
SRCH-17A term that matches nothing states that nothing matched it, and names how many files were searched.
SRCH-18Search only finds. Nothing in the app changes what a search has found, in one file or across the vault.

08 MUT — Creating, renaming, moving, deleting

IDRule
MUT-1Five operations exist: create a file, create a folder, rename an entry, move an entry, delete an entry.
MUT-3Creation happens inside the selected folder. When a file is selected, creation happens in the folder that holds it. When nothing is selected, creation happens at the root of the vault.
MUT-4Naming happens in the tree itself: the row becomes a text field. Enter commits the name, Escape cancels the operation, and clicking away commits.
MUT-5The user types the extension. The app never adds one, never completes one and never offers a list to pick from.
MUT-6Creating a file whose extension is not one of the six is refused. A name with no extension is refused for the same reason.
MUT-7Renaming may not leave a supported file unsupported. Renaming a file that was already unsupported is unrestricted, because it was never openable.
MUT-8A name already used by another entry in the same folder is refused.
MUT-9A refusal keeps the text field open with the name the user typed, and states the reason underneath. Nothing is written to disk. The user corrects the name or presses Escape.
MUT-10Deleting a file asks the user to confirm, and names the file.
MUT-11Deleting a folder requires the user to type the folder's name. The prompt states how many files are removed with it.
MUT-12When anything being deleted has unsaved changes in a tab, the prompt says so before asking for the confirmation.
MUT-13Deletion is permanent. The app has no trash and no undo, and every deletion prompt says so.
MUT-14Renaming a folder keeps everything inside it. Tabs open on files inside that folder follow the rename and stay open.
MUT-15An operation that fails on disk reports the reason from the system and changes nothing in the tree.
MUT-16An entry moves two ways: dragging its row, or cutting it with Cmd/Ctrl+X and pasting into the target with Cmd/Ctrl+V. Both move one entry at a time.
MUT-17Dropping onto a folder row moves the entry into that folder. Dropping onto a file row moves it into the folder that holds that file. Dropping onto the panel background, away from every row, moves it to the root of the vault.
MUT-18While a drag is over a valid target, that target is highlighted. A target that would refuse the move is not highlighted.
MUT-19Dropping onto a collapsed folder moves the entry in and expands that folder, so the user sees where it landed.
MUT-20A move into a folder that already holds that name is refused, and nothing is moved. The reason is the one in MUT-8.
MUT-21A folder cannot be moved into itself or into anything inside itself. A move onto the folder that already holds the entry does nothing.
MUT-22A move never changes a name, so the extension rules in MUT-6 and MUT-7 do not apply to it.
MUT-23A save still pending on a moved file is written before the move starts. No write is ever in flight while a path changes.
MUT-24An open tab follows its file to the new path and stays open. Moving a folder carries every open tab inside it.
MUT-25Moving is permanent. As with deletion, there is no undo.
MUT-26Dragging and pasting are refused while a filter is active, because a filtered tree hides the folders the user needs as targets. The refusal says to clear the search first.

09 TAB — Tabs

IDRule
TAB-1The tab bar lists the open files in the order they were opened. The order is fixed and tabs cannot be dragged.
TAB-2At most five files are open at once. Opening a sixth is refused with a message that names the limit and asks the user to close a tab first. Nothing is closed automatically.
TAB-3Opening a file that is already open activates its existing tab. It does not open a second tab and does not count against the limit again.
TAB-4Each tab shows the file name and its save state. See DOC-5.
TAB-5A tab closes through its close control or a middle click.
TAB-6Closing the active tab activates the tab to its right, or the tab to its left when the closed tab was the last one. Closing a tab that is not active leaves the active tab alone.
TAB-7Closing the last tab shows the empty state described in FEED-1.
TAB-8Closing a tab with a save still pending writes the file first, then closes.
TAB-9Closing a tab whose conflict is unresolved, or whose last save failed, asks the user to confirm losing the changes.
TAB-10Only the active tab's viewer is shown. Exactly one viewer is visible whenever at least one tab is open.

10 DOC — Saving

IDRule
DOC-1An edit reaches the disk without a command from the user. Saving by hand is never required.
DOC-2A save runs 600 ms after the last change to a document, and at the latest 3 s after the first unsaved change. The second half of that rule covers a user who types without pausing.
DOC-3Three actions save immediately instead of waiting: pressing Cmd/Ctrl+S, switching to a different tab in the app, and leaving the browser tab.
DOC-4DOC-2 and DOC-3 apply to every editable kind: drawings, Markdown and plain text. Drawing is an edit like typing is an edit.
DOC-5Each tab shows one of four save states: unsaved changes, saving, saved, failed.
DOC-6One status line beside the tab bar states the state of the app as a whole: Saving…, All changes saved, Save failed, or Offline.
DOC-7A save that fails for a reason other than a conflict is reported at once, with the reason the system gave. The app does not retry on its own. Automatic saving of that file stops until the user asks to try again.
DOC-8A failed save never discards content. The document stays in the viewer exactly as the user left it.
DOC-9HTML files are never written. See HTML-5.
DOC-10Line endings are preserved. A file that used CRLF still uses CRLF after the app saves it.
DOC-11A byte-order mark at the start of a file is preserved.
DOC-12A save either replaces the whole file or leaves it as it was. A file is never left half written, whatever interrupts the save.

11 SYNC — Changes made outside the app

IDRule
SYNC-1A change made to the vault outside the app appears in the app without a reload.
SYNC-2The tree follows those changes: new entries appear, removed entries disappear. The selected row stays selected and expanded folders stay expanded, as long as they still exist.
SYNC-3An open file with no unsaved changes reloads from disk in place, and the user sees the new content in the viewer.
SYNC-4An open file with unsaved changes never reloads silently. It raises a conflict instead. See CONF-1.
SYNC-5When an open file disappears from disk: a tab with no unsaved changes closes; a tab with unsaved changes stays open, marked as deleted on disk, its automatic saving stopped, offering one action that writes the content back and recreates the file.
SYNC-6A file renamed or moved outside the app counts as one entry removed and another added, so an open tab on it follows SYNC-5. A rename or a move performed inside the app follows the file instead, because the app knows both paths.
SYNC-7When the app loses contact with the vault, the status line says Offline and the app keeps trying to restore it.
SYNC-8Once contact is restored, the app re-checks the whole vault and every open file. A clean file whose content changed reloads. A file with unsaved changes whose content changed raises a conflict.
SYNC-9The app's own saves do not count as outside changes. Saving a file never reloads the viewer the user is working in.

12 CONF — Conflicts

IDRule
CONF-1A conflict exists when a document has unsaved changes and the file on disk changed after the app read it.
CONF-2A conflict opens a modal that names the file and offers exactly two choices. Overwrite the file writes the app's version over the file on disk. Discard my changes throws the app's version away and loads the file from disk.
CONF-3The modal cannot be dismissed. Escape does nothing and clicking outside does nothing. One of the two choices ends it.
CONF-4Automatic saving of that file stops while its modal is open. Every other open file keeps saving normally.
CONF-5Conflicts queue. One modal is shown at a time, and it states how many other files are waiting.
CONF-6For a drawing, the discard choice is worded as discarding the drawing as it stands now. The user cannot compare two versions of a drawing, so the modal names what is lost instead of implying a comparison.
CONF-7Either choice clears the conflict and returns the file to normal automatic saving.
CONF-8A conflict never resolves itself and never expires. It waits for the user.
CONF-9A conflict does not block the rest of the app. The user can still browse the tree and edit other open files.

13 VIEW — Viewers in general

IDRule
VIEW-1The extension decides the viewer. The user cannot pick a different one.
VIEW-2Switching between tabs and back leaves each viewer's content as it was. Switching tabs is not a reload.
VIEW-3Renaming an open file so that its kind changes reloads it into the viewer that matches the new extension.
VIEW-4A viewer that cannot show its file — the content does not parse, or the file is unreadable — states the reason in the pane instead of showing an empty surface.

14 EX — Drawing viewer

IDRule
EX-1An .excalidraw file opens as a drawing surface with the full tool set of Excalidraw. The app adds no tools of its own and removes none.
EX-2Drawing is editing. Changes save under the DOC rules, with no save command.
EX-3Files stay interchangeable with excalidraw.com. A drawing the app saved opens there, and a drawing saved there opens in the app.
EX-4An image pasted into a drawing is kept, saved with the drawing and still there when the file is reopened.
EX-5A file whose content is not a valid drawing is refused with a message naming the reason. No empty canvas is shown in its place, because saving that canvas would destroy the file.
EX-6Panning and zooming are not edits and never cause a save.

15 MD — Markdown viewer

IDRule
MD-1The pane splits in two: the Markdown source on the left, the rendered document on the right.
MD-2The rendered side follows the source as the user types. No command is needed to refresh it.
MD-3Either side can be collapsed, so the user can work in source alone or read the rendered document alone. The choice applies to the app, not to one file, and it survives a reload.
MD-4Rendering covers standard Markdown plus tables, task lists, strikethrough and fenced code blocks.
MD-5An image whose path is relative to the file renders from the vault.
MD-6A link to a supported file inside the vault opens that file as a tab, under the TAB rules.
MD-7A link to a file that is missing or unsupported shows the refusal message from FEED-2 and opens nothing.
MD-8An http or https link opens in a new browser tab. The app itself is never navigated away.
MD-9The rendered document holds no active content. Scripts and event handlers written into the Markdown are removed before it is shown.
MD-10Editing happens only in the source side. The rendered side is not editable.
MD-11The two sides scroll independently.

16 TXT — Text viewer

IDRule
TXT-1A .txt file opens in a plain text editor: no rendering, no preview, no syntax colouring.
TXT-2The editor shows the file as it is. It does not wrap, reflow or reformat the content on load or on save.
TXT-3Editing and saving follow the DOC rules, including DOC-10 and DOC-11.

17 HTML — HTML viewer

IDRule
HTML-1An .html or .htm file opens rendered, as the file would appear in a browser.
HTML-2Images, stylesheets and scripts referenced by a path relative to the file load from the vault. A page and its assets look the same in the app as they do when opened directly.
HTML-3Scripts in the page run.
HTML-4The page is isolated from the app. It cannot read or change anything around it, and it cannot navigate the app away.
HTML-5There is no editing: no source view, no save, no way for the app to write an HTML file.
HTML-6A change to the file on disk re-renders the page. See SYNC-3. An HTML file can never have unsaved changes, so it never conflicts.

18 FEED — Messages and empty states

IDRule
FEED-1With no tab open, the viewer pane names the vault, lists the four kinds the app can open, and states that a file opens on a double click.
FEED-2A double click on an unsupported file shows a short message naming the extension and stating that the app cannot open it. The row stays visibly marked as not openable, so the refusal is never the user's first hint.
FEED-3Every refusal names its reason: unsupported extension, name already taken, file too large, file is not text, tab limit reached.
FEED-4A message appears next to the thing that caused it. A refused name is explained under the text field; a refused open is explained near the tab bar.
FEED-5No state is communicated by colour alone. Save state, conflict state and unopenable rows each carry a shape or a word as well.
FEED-6An empty folder expands to show that it is empty, rather than looking like a folder that failed to open.

19 SESS — What survives a reload

IDRule
SESS-1A reload restores the open tabs, the active tab, the expanded folders, the selected row, the tree panel width and the Markdown pane choice from MD-3.
SESS-2A restored path that no longer exists, or that is no longer supported, is dropped without a message. A reload never shows an error about a file the user has already moved on from.
SESS-3Cursor position and scroll position are not restored.
SESS-4Unsaved changes are not restored. They were written to disk before the reload, or they were lost with the page — the app keeps no draft of its own.
SESS-5The search term is not restored. A reload clears the field and shows the whole tree, because a filter is a momentary act and not part of the workspace.

20 Document lifecycle

Every open file is in exactly one of these states. The table is the authority on which transitions exist.

StateMeaningLeaves the state when
LoadingThe file is being read.The content arrives, and the state becomes Saved. A refusal closes the tab and shows a message.
SavedThe document matches the file on disk.The user edits it, and the state becomes Unsaved. The file changes on disk, and the document reloads, staying Saved.
UnsavedThe document differs from the file. A save is scheduled.The save starts, and the state becomes Saving. The file changes on disk first, and the state becomes Conflict.
SavingThe save is in progress.It succeeds, and the state becomes Saved. It is rejected as stale, and the state becomes Conflict. It fails otherwise, and the state becomes Failed.
ConflictThe document has unsaved changes and the file changed underneath it. Automatic saving is stopped.The user chooses to overwrite, and the state becomes Saving. The user chooses to discard, and the document reloads as Saved.
FailedThe last save failed for a reason other than a conflict. Automatic saving is stopped.The user asks to try again, and the state becomes Saving.
DeletedThe file is gone from disk and the document has unsaved changes. Automatic saving is stopped.The user writes it back, and the state becomes Saving. The user closes the tab, confirming the loss.

A document with no unsaved changes never reaches Conflict, Failed or Deleted. Its tab closes instead, under SYNC-5, or its content reloads, under SYNC-3.

21 Conformance walk

Each walk is performed in the running app against a vault holding at least one file of each supported kind, one unsupported file, and folders nested three deep. A walk passes only when every rule it names holds.

W1 — Browsing

  1. Expand three levels, then collapse the top one. Expand it again: the inner folders are collapsed. TREE-3 TREE-4
  2. Click a file once. Nothing opens. TREE-2
  3. Walk to a file with the arrow keys and press Enter. It opens. TREE-5
  4. Double-click the unsupported file. A message names its extension and no tab opens. VAULT-3 FEED-2

W2 — Tabs

  1. Open five files, then a sixth. The sixth is refused and the message names the limit. Nothing closed. TAB-2
  2. Double-click one of the five again. Its tab activates; no sixth tab appears. TAB-3
  3. Close the active middle tab. Its right neighbour activates. TAB-6
  4. Close the last remaining tab. The hint panel appears. TAB-7 FEED-1

W3 — Saving

  1. Type into a Markdown file and stop. Within a second the status line reads All changes saved, and the file on disk holds the new text. DOC-2 DOC-6
  2. Type without pausing for ten seconds. The file changed on disk before the typing stopped. DOC-2
  3. Draw in a drawing, switch to another tab and back. The drawing is there, and the file holds it. DOC-4 VIEW-2
  4. Make a file read-only outside the app, then edit it. The failure is reported at once with the system's reason, the tab shows the failed state, and the content stays in the editor. DOC-7 DOC-8
  5. Edit a file that used CRLF. It still uses CRLF. DOC-10

W4 — Outside changes

  1. With a file open and saved, change it outside the app. The viewer shows the new content. SYNC-3
  2. Create a file and a folder outside the app. Both appear in the tree, and the selected row and expanded folders are undisturbed. SYNC-2 TREE-8
  3. Delete an open, saved file outside the app. Its tab closes. SYNC-5
  4. Type into a file, and while the change is unsaved, delete the file outside the app. The tab stays, marked deleted, and writing it back recreates the file. SYNC-5
  5. Stop the app's contact with the vault, change two files, restore contact. A clean open file reloads; a dirty one raises a conflict. SYNC-7 SYNC-8

W5 — Conflicts

  1. Type into a file and, before the save lands, replace the file outside the app. A modal names the file and offers two choices. CONF-1 CONF-2
  2. Press Escape and click outside the modal. It stays. CONF-3
  3. Choose to overwrite. The file holds the app's version. CONF-7
  4. Repeat, and choose to discard. The viewer holds the disk version. CONF-7
  5. Force conflicts on two files at once. One modal appears and states that another waits. CONF-5
  6. Force a conflict on a drawing. The discard choice names the drawing as what is lost. CONF-6
  7. While a conflict is open, edit a different file. It saves normally. CONF-4 CONF-9

W6 — Creating, renaming, deleting

  1. Create a file named note. It is refused for having no extension. Correct it to note.md and it is created. MUT-6 MUT-9
  2. Create a second file with the same name. It is refused. MUT-8
  3. Rename note.md to note.bak. It is refused. MUT-7
  4. Rename it to notes.md while it is open. The tab follows the new name. MUT-14 SYNC-6
  5. Create a folder with no selection. It lands at the vault root. MUT-3
  6. Delete a folder. Typing its name is required, and the prompt states how many files go with it. MUT-11
  7. Delete a file that has unsaved changes. The prompt says so before asking. MUT-12

W7 — Viewers

  1. Open a Markdown file holding a relative image, a link to another vault file, and an external link. The image renders; the vault link opens a tab; the external link opens a browser tab and the app stays put. MD-5 MD-6 MD-8
  2. Collapse the rendered side, reload the page, and it is still collapsed. MD-3 SESS-1
  3. Open an HTML file that loads a relative stylesheet and runs a script. Both work, and no editing surface is offered. HTML-2 HTML-3 HTML-5
  4. Open a drawing saved by excalidraw.com, edit it, and open the file there again. It still opens. EX-3
  5. Paste an image into a drawing, reopen the tab, and the image is still there. EX-4
  6. Rename a .excalidraw file to .txt to break it, then open it. It is refused with a reason and no empty canvas appears. EX-5 VIEW-4

W8 — Shell

  1. Type into a file and immediately try to close the browser tab. The browser asks for confirmation. APP-5
  2. Reload the page. The same tabs, the same active tab, the same expanded folders and the same panel width come back. SESS-1
  3. Delete a file outside the app, then reload. Its tab is gone and no error is shown. SESS-2
  4. Open the app in a second browser tab, and edit the same file in both. The second save raises a conflict. APP-4

W9 — Search

  1. Type one character. Rows are filtered on names, and each match is shown under its real folders. SRCH-2 SRCH-10
  2. Type a word that appears inside a Markdown file but in no file name. That file appears, with a count of its occurrences. SRCH-5 SRCH-13
  3. Type a word written into a shape in a drawing. The drawing appears. Type an identifier from the drawing's raw data. It does not. SRCH-6
  4. Open the result. The Markdown file scrolls to its first match; the drawing opens without jumping. SRCH-14
  5. Type a word only in an unsaved edit that has not reached disk. The file matches. SRCH-12
  6. With a filter active, create a matching file outside the app. It appears in the results. Delete it. It goes. SRCH-15
  7. Type a term that matches nothing. The panel says so and names how many files were searched. SRCH-17
  8. Clear the field. The tree returns with the same expanded folders and the same selected row as before the search. SRCH-3
  9. Reload the page. The field is empty and the whole tree is shown. SESS-5
  10. Search for a word held only by a file in an excluded folder. Nothing matches. SRCH-8

W10 — Moving

  1. Drag a file onto a collapsed folder. It moves in and the folder expands. MUT-17 MUT-19
  2. Drag a file onto another file. It lands in that file's folder, not on the file. MUT-17
  3. Drag a file from a nested folder onto the panel background. It lands at the root of the vault. MUT-17
  4. Select a file, press Cmd/Ctrl+X, select a folder, press Cmd/Ctrl+V. It moves. MUT-16
  5. Move a file into a folder that already holds that name. The move is refused and nothing changed. MUT-20
  6. Drag a folder onto one of its own children. The target is never highlighted and the drop is refused. MUT-18 MUT-21
  7. Move a folder holding two open files. Both tabs stay open on the new paths. MUT-24
  8. Type into a file and immediately move it. The edit is on disk at the new path, not the old one. MUT-23
  9. Type a term into the search field, then try to drag a row. The drag is refused and the message says to clear the search. MUT-26

22 Out of scope

These are named so they are not assumed to exist.

  • Multiple selection. Every operation acts on one entry. There is no way to select several rows, so nothing can be moved, deleted or opened in bulk.
  • Undo, and a trash. Deleting and moving are permanent. The app keeps no history and no recycle folder.
  • Replace. Search finds; it never changes what it finds, in one file or across the vault.
  • Version control, accounts, several vaults. No git integration, no sharing, no second vault inside one running app.
